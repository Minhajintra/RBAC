INTRASHIP — USER & ACCESS MANAGEMENT (UAM) ENTERPRISE PORTAL
PROJECT FOLDER STRUCTURE, FILE-BY-FILE PURPOSE, AND SYSTEM FLOW SPECIFICATION
================================================================================

PROJECT OVERVIEW:
IntraShip UAM is a production-grade enterprise User and Access Management portal built 
with Next.js 15 (App Router), React 19, TypeScript, and Tailwind CSS. It supports 
Role-Based Access Control (RBAC), multi-factor authentication (MFA/OTP), jurisdictional 
scope assignment (Province -> Region -> District -> Sub-district -> Site), audit 
logging with CSV exports, dynamic analytics charts, and seamless fallback between a 
live FastAPI backend and local JSON mock persistence.

3. FILE-BY-FILE PURPOSE (DETAILED EXPLANATION OF EVERY FILE)
================================================================================

--------------------------------------------------------------------------------
3.1 ROOT CONFIGURATION & ENVIRONMENT FILES
--------------------------------------------------------------------------------
1. .env
   - Purpose: Environment variables file for local development. Holds 
     `BACKEND_BASE_URL` (the backend server address e.g. FastAPI URL or tunnel URL) 
     and public API configuration flags.

2. .gitignore
   - Purpose: Git source-control ignore rules. Excludes node_modules, .next build 
     outputs, environment files (.env.local), and system build info from commits.

3. eslint.config.mjs
   - Purpose: Modern flat ESLint configuration file for Next.js and TypeScript. 
     Configures code quality rules and syntax linting standards.

4. next-env.d.ts
   - Purpose: TypeScript compiler definition file automatically maintained by 
     Next.js. Ensures TypeScript recognizes Next.js types and image imports.

5. next.config.ts
   - Purpose: Next.js application configuration file written in TypeScript. 
     Configures compiler options, asset prefixes, rewrites, and experimental flags.

6. package.json
   - Purpose: Node.js project manifest. Defines project metadata, build scripts 
     (`npm run dev`, `build`, `start`, `lint`), and all production / dev dependencies.

7. package-lock.json
   - Purpose: Automatically generated exact dependency lockfile ensuring identical 
     package installations across different developer environments.

8. postcss.config.js
   - Purpose: PostCSS configuration file. Connects Tailwind CSS and Autoprefixer 
     to process utility styles for browser compatibility.

9. README.md
   - Purpose: Project documentation and quick-start instructions for developers.

10. tailwind.config.js
    - Purpose: Tailwind CSS design system configuration. Defines theme colors 
      (IntraShip custom forest green shades like #16382b, #225740), font families, 
      screen breakpoints, and content file paths.

11. tsconfig.json
    - Purpose: TypeScript compiler options configuration. Sets target ECMAScript 
      version, module resolution, strict mode, and path aliases (e.g. `@/*` -> `./src/*`).

12. tsconfig.tsbuildinfo
    - Purpose: Incremental TypeScript build cache generated by `tsc` to speed up 
      type-checking during successive runs.

--------------------------------------------------------------------------------
3.2 LOCAL PERSISTENCE & PUBLIC ASSETS
--------------------------------------------------------------------------------
13. .data/users-store.json
    - Purpose: Server-side runtime JSON database for persisting user operations 
      (create, edit, delete, toggle status, assign scope) during local testing 
      when a live backend database is offline.

14. public/favicon.ico
    - Purpose: Browser tab icon representing the IntraShip portal.

15. public/images/login-bg.webp
    - Purpose: High-resolution branded background illustration used on the 
      login and authentication split-screen pages.

--------------------------------------------------------------------------------
3.3 APPLICATION CORE & GLOBAL LAYOUTS (src/app, src/middleware.ts)
--------------------------------------------------------------------------------
16. src/middleware.ts
    - Purpose: Edge middleware executed before requests reach page routes. 
      Inspects the `uam_verified` authentication cookie. If an unverified user 
      attempts to access `/dashboard` or `/users`, it redirects them to `/login`. 
      If an already verified user visits `/login`, it redirects them to `/dashboard`.

17. src/app/globals.css
    - Purpose: Root global CSS stylesheet importing Tailwind directives (@tailwind base, 
      components, utilities) and setting global scrollbar and typography rules.

18. src/app/layout.tsx
    - Purpose: Root HTML shell layout wrapping the entire application. Injects 
      HTML/body tags, global metadata, font styles, and wraps all pages inside 
      `<AuthProvider>`.

19. src/app/not-found.tsx
    - Purpose: Custom 404 error page displayed when users navigate to non-existent 
      routes. Features enterprise styling and a direct button to return to `/dashboard`.

20. src/app/page.tsx
    - Purpose: Application entry root route (`/`). Uses Next.js `redirect("/login")` 
      to automatically send visitors straight to the login portal.

--------------------------------------------------------------------------------
3.4 AUTHENTICATION MODULE (src/app/(auth)/...)
--------------------------------------------------------------------------------
21. src/app/(auth)/layout.tsx
    - Purpose: Route group layout for authentication screens (login, verify-otp, 
      forgot-password, reset-password). Provides a clean wrapper without the dashboard sidebar.

-- Login Sub-Module:
22. src/app/(auth)/login/page.tsx
    - Purpose: The main login screen. Renders IntraShip branding, security badges, 
      system mission statements, and embeds the `<LoginForm />`.

23. src/app/(auth)/login/actions/login.ts
    - Purpose: Server Action `loginAction(payload)` invoked by the login form. 
      Delegates the authentication request to `authService.login()`.

24. src/app/(auth)/login/components/LoginForm.tsx
    - Purpose: Client-side interactive login form. Uses React Hook Form with Zod 
      validation, email/username input, password visibility toggle, remember-me checkbox, 
      and triggers transition to OTP verification on valid credentials.

25. src/app/(auth)/login/schema/loginSchema.ts
    - Purpose: Zod schema enforcing validation rules for the login form (e.g. required 
      identifier, password minimum length, custom error messages).

26. src/app/(auth)/login/types/login.types.ts
    - Purpose: TypeScript interface definitions for login credentials (`LoginRequest`), 
      authenticated user payload (`AuthUser`), and API responses (`LoginResponse`).

-- Verify OTP (2FA) Sub-Module:
27. src/app/(auth)/verify-otp/page.tsx
    - Purpose: Multi-Factor Authentication screen. Prompts the user to enter a 
      6-digit one-time verification code sent to their registered email.

28. src/app/(auth)/verify-otp/actions/verifyOtp.ts
    - Purpose: Server Action `verifyOtpAction(payload)` delegating verification 
      code validation to `authService.verifyOtp()`.

29. src/app/(auth)/verify-otp/components/VerifyOtpForm.tsx
    - Purpose: Interactive OTP input component featuring 6 individual auto-advancing 
      digit boxes, countdown timer, resend OTP trigger, and dev-code auto-population helper.

30. src/app/(auth)/verify-otp/schema/verifyOtpSchema.ts
    - Purpose: Zod validation schema ensuring the OTP code consists of exactly 6 
      numeric digits.

31. src/app/(auth)/verify-otp/types/verifyOtp.types.ts
    - Purpose: TypeScript types for OTP request (`VerifyOtpRequest`), OTP delivery 
      payload (`SendOtpRequest`), and server response envelopes.

-- Forgot Password Sub-Module:
32. src/app/(auth)/forgot-password/page.tsx
    - Purpose: Password recovery initiation page where users enter their email 
      to receive a password reset token/code.

33. src/app/(auth)/forgot-password/actions/forgotPassword.ts
    - Purpose: Server Action `forgotPasswordAction(payload)` invoking `authService.forgotPassword()`.

34. src/app/(auth)/forgot-password/components/ForgotPasswordForm.tsx
    - Purpose: Form component allowing users to submit their email address with 
      loading states and instant feedback.

35. src/app/(auth)/forgot-password/schema/forgotPasswordSchema.ts
    - Purpose: Zod schema validating email formatting for the password reset request.

36. src/app/(auth)/forgot-password/types/forgotPassword.types.ts
    - Purpose: TypeScript contracts for forgot password request and response objects.

-- Reset Password Sub-Module:
37. src/app/(auth)/reset-password/page.tsx
    - Purpose: Final password update page where users set and confirm their new password.

38. src/app/(auth)/reset-password/actions/resetPassword.ts
    - Purpose: Server Action `resetPasswordAction(payload)` updating the password 
      via `authService.resetPassword()`.

39. src/app/(auth)/reset-password/components/ResetPasswordForm.tsx
    - Purpose: Form component featuring password strength checks, confirm-password 
      matching validation, and submission feedback.

40. src/app/(auth)/reset-password/schema/resetPasswordSchema.ts
    - Purpose: Zod schema enforcing strong password requirements (uppercase, lowercase, 
      numbers, special characters, minimum length) and confirm password equality.

41. src/app/(auth)/reset-password/types/resetPassword.types.ts
    - Purpose: TypeScript types for password reset payload (`ResetPasswordRequest`) 
      and API confirmation responses.

4. SYSTEM ARCHITECTURE & END-TO-END FLOWS
================================================================================

--------------------------------------------------------------------------------
4.1 FLOW 1: AUTHENTICATION & TWO-FACTOR (OTP) FLOW
--------------------------------------------------------------------------------
Step 1: User visits `/login` and fills in email/username and password.
Step 2: `<LoginForm />` validates inputs using `loginSchema.ts` (Zod).
Step 3: On submit, client invokes `loginAction(payload)` -> `authService.login()`.
Step 4: Request reaches Next.js Route Handler `POST /api/auth/login`.
Step 5: The route handler calls the backend endpoint `/api/v1/auth/login`.
        - If valid, the backend accepts credentials.
        - Next.js sets temporary HTTP-only cookies:
          - `uam_pending_email`: User's authenticated email.
          - `uam_pending_token`: Partial access token.
Step 6: User is automatically redirected to `/verify-otp`.
Step 7: `<VerifyOtpForm />` renders 6 digit inputs and prompts user for OTP.
Step 8: User enters 6 digits -> calls `POST /api/auth/verify-otp`.
Step 9: Backend verifies OTP code against `/api/v1/auth/otp/verify` (or dev code fallback).
Step 10: Upon successful verification:
         - Secure HTTP-only cookies are established:
           - `uam_verified = "true"` (Session indicator)
           - `uam_auth_token` (Access JWT)
           - `uam_refresh_token` (Long-lived refresh JWT)
         - In-memory `authStorage.setAccessToken(token)` is populated.
         - User is routed to `/dashboard`.

--------------------------------------------------------------------------------
4.2 FLOW 2: ROUTE PROTECTION & MIDDLEWARE GUARD FLOW
--------------------------------------------------------------------------------
Step 1: Whenever a request is made to `/dashboard/*` or `/users/*`, `src/middleware.ts` 
        intercepts the request at the edge.
Step 2: It checks the cookie `uam_verified`.
Step 3: If `uam_verified !== "true"`:
        - Request is redirected to `/login?from=<requested_path>`.
Step 4: If an already authenticated user navigates to `/login`:
        - Middleware intercepts and redirects directly to `/dashboard`.
Step 5: When the user clicks "Logout" in `<Sidebar />`:
        - `authService.logout()` invokes `POST /api/auth/logout`.
        - Server deletes all session cookies.
        - Client clears in-memory tokens and redirects to `/login`.

--------------------------------------------------------------------------------
4.3 FLOW 3: ROLE-BASED ACCESS CONTROL (RBAC) & PERMISSION GUARD FLOW
--------------------------------------------------------------------------------
Step 1: User enters `/dashboard` or any protected page.
Step 2: `(dashboard)/layout.tsx` mounts `<PermissionProvider>`.
Step 3: `PermissionProvider` queries `permissionService.getMyPermissions()`.
Step 4: Permissions are loaded from `/api/v1/me/permissions` (or `permissions.json`).
Step 5: Throughout the UI, elements are wrapped in `<PermissionGuard>`:
        - Example: `<PermissionGuard module="users" action="create">`
        - If user role lacks "can_create" for "users", the "Add User" button is hidden 
          or rendered as disabled.
Step 6: Navigation links in `<Sidebar />` inspect `isVisible(module)`:
        - If a user's role cannot view "audit", the Audit Logs sidebar link is omitted.

--------------------------------------------------------------------------------
4.4 FLOW 4: USER MANAGEMENT (CRUD) & STORE PERSISTENCE FLOW
--------------------------------------------------------------------------------
1. Read / Search / Filter:
   - `<UsersModule />` calls `getUsersAction({ search, role, status, page, pageSize })`.
   - `users.ts` server action attempts to query `/api/v1/users/user-list`.
   - If backend is offline, it queries `userDataAccess.ts`, which reads from 
     `.data/users-store.json`.
   - Filtered, paginated users list and computed stats are returned to `<UserTable />`.

2. Create User:
   - Admin clicks "+ Add User" -> Opens `<UserFormModal />`.
   - Form validates fields using `createUserSchema.ts`.
   - On submit, calls `createUserAction(formData)`.
   - User record is persisted to backend / `.data/users-store.json`.
   - `revalidatePath("/users")` updates the UI with a success toast.

3. Edit User:
   - Admin clicks "Edit" on a table row -> Opens `<UserFormModal editingUser={user} />`.
   - Admin submits updates -> calls `updateUserAction(user.id, updates)`.
   - Record updates in store; table updates instantly.

4. Toggle Activation:
   - Admin clicks "Activate / Deactivate" in row menu.
   - Calls `toggleUserStatusAction(userId)`.
   - Status switches between "Active" and "Inactive".

5. Delete User:
   - Admin clicks "Delete" -> Opens `<DeleteUserDialog />`.
   - Admin confirms -> calls `deleteUserAction(userId)`.
   - Record is removed and user count recomputed.

--------------------------------------------------------------------------------
4.5 FLOW 5: JURISDICTIONAL SCOPE HIERARCHY ASSIGNMENT FLOW
--------------------------------------------------------------------------------
Step 1: Admin selects "Assign Scope" on any user in `<UserTable />`.
Step 2: `<UserScopeModal />` opens, displaying cascading dropdowns:
        - 1. Select Workspace (e.g. "Primary Education", "Logistics Hub")
        - 2. Select Province (e.g. "Sindh", "Punjab")
        - 3. Select Region (cascades based on Province)
        - 4. Select District (cascades based on Region)
        - 5. Select Sub-District
        - 6. Select Site (specific school, office, or facility)
Step 3: On save, `scopeService.assignUserScope(userId, payload)` sends a PUT 
        request to `/api/v1/users/{userId}/scope`.
Step 4: The user's operational jurisdiction is locked and reflected in `<ViewUserModal />`.

--------------------------------------------------------------------------------
4.6 FLOW 6: DASHBOARD ANALYTICS & KPI DATA FLOW
--------------------------------------------------------------------------------
Step 1: User navigates to `/dashboard`.
Step 2: `<Dashboard.tsx>` triggers parallel Server Actions:
        - `getDashboardKpis()`: Fetches summary metrics for `<KpiCardsGrid />`.
        - `getRoleUsers()`: Populates the donut chart in `<RoleUsersChart />`.
        - `getLoginAttempts("daily" | "monthly")`: Populates `<LoginAttemptsChart />`.
        - `getInterfaceAccess()`: Populates the area/bar `<InterfaceAccessChart />`.
        - `getLoginHistoryAction()`: Populates `<LoginHistoryTable />`.
        - `getSecurityOverviewAction()`: Populates `<SecurityWidget />`.
Step 3: Charts render with smooth animations via Recharts.
Step 4: Users can switch tabs (e.g. Daily vs Monthly) to trigger dynamic re-fetches.

--------------------------------------------------------------------------------
4.7 FLOW 7: ROLES & PERMISSION MATRIX AUTHORING FLOW
--------------------------------------------------------------------------------
Step 1: Admin navigates to `/roles` or `/roles/create`.
Step 2: `<CreateEditRoleModule />` renders a matrix table listing all system screens:
        - Dashboard, Users, Roles & Permissions, Audit Logs, Settings.
Step 3: For each screen, checkboxes toggle:
        - Screen Reachable (Visibility)
        - Can Create
        - Can Read
        - Can Update
        - Can Delete
Step 4: Admin enters Role Name and Description, then clicks "Save Role".
Step 5: `saveRoleAction(roleData, matrix)` posts configuration to `/api/v1/roles/create`.
Step 6: New role becomes immediately available in User Creation dropdowns.

--------------------------------------------------------------------------------
4.8 FLOW 8: AUDIT LOGGING & TRACEABILITY FLOW
--------------------------------------------------------------------------------
Step 1: Admin visits `/audit`.
Step 2: `<AuditLogsModule />` calls `getAuditLogsAction()`.
Step 3: Logs are loaded from `/api/v1/audit/audit-logs` or fallback `audit-logs.json`.
Step 4: Admin can search logs by user name, action type (e.g. "UPDATE_USER", "LOGIN"), 
        or status ("Success" / "Failed").
Step 5: Admin clicks "Export CSV":
        - Action `exportAuditLogsAction()` formats logs into standard RFC 4180 CSV text.
        - Browser automatically prompts download for `audit-logs-<timestamp>.csv`.

--------------------------------------------------------------------------------
4.9 FLOW 9: BACKEND CONNECTION & OFFLINE FALLBACK ARCHITECTURE
--------------------------------------------------------------------------------
1. Live Backend Mode:
   - When `BACKEND_BASE_URL` is reachable, all requests pass through Axios (`api-client.ts`) 
     to FastAPI endpoints.
   - Authentication tokens are attached automatically via request interceptors.

2. Resilient Offline / Dev Fallback Mode:
   - If the backend is down or unreachable during local development, the application 
     never crashes with a blank screen.
   - Next.js Route Handlers and Server Actions catch network connection errors and 
     gracefully switch to local mock databases (`.data/users-store.json`, `mock/*.json`).
   - Standard development OTP code (`123456` or `000000`) allows continuous full-flow 
     testing without email server dependency.
